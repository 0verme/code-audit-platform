# 内网部署前配置预检

本文只覆盖部署配置、运行边界和预检，不改变 HCYT、NUPS、FineReport 的业务语义或 API 契约。

## 结论与阻断项

- 推荐数据库 Profile：`inner_dws`（`type: dws`）。当 `CODE_AUDIT_DEPLOYMENT_MODE=inner` 或 `production` 时，应用拒绝以任何其他 Profile 启动。
- 正式后端入口：Linux/Kylin 使用 `waitress-serve --host=0.0.0.0 --port=5088 app:app`，由 Nginx 代理 `/api/`；不要使用 Flask debug server。
- 前端生产地址使用相对路径 `/api`。不要把 `localhost`、开发端口或内网 IP 编译进生产包。
- 必须在部署机创建未跟踪的 `backend/configs/database.yaml` 和 `backend/configs/svn.yaml`。仓库只保留脱敏模板。
- 内网 DWS 与 SVN 未在当前环境连接；以下检查 SQL/命令必须在内网执行，不能视为已验证通过。

## 配置加载链路

```text
进程环境变量
  -> backend/.env（仅补齐未设置的变量）
  -> AUDIT_DATABASE_CONFIG 或 backend/configs/database.yaml
  -> default_profile / CODE_AUDIT_DB_PROFILE
  -> Profile 字段默认值（table_prefix=dwp 的运行表前缀约定）
```

`database.yaml` 中完整值为 `${NAME}` 时会由进程环境变量替换；缺失的必填字段会在启动阶段明确报错。`inner`/`production` 模式还会强制 `inner_dws` + `dws`，不会降级到 SQLite。SQLite 仅保留给测试和迁移工具，不能作为内网正式库。

| 场景 | 数据库 | 前端 | 本地目录审计 |
| --- | --- | --- | --- |
| 开发/测试 | 可使用测试 Profile 或测试 SQLite 注入 | 可用 Vite 开发地址 | 按需显式启用并配置根目录 |
| 内网 | `inner_dws` / DWS | `/api` 经 Nginx | 默认关闭 |

## 必填配置

从 `backend/configs/database.example.yaml` 复制到部署机的 `database.yaml`，从 `backend/.env.example` 复制为部署机私有 `.env`。必填变量：

```text
CODE_AUDIT_DEPLOYMENT_MODE=inner
CODE_AUDIT_DB_PROFILE=inner_dws
AUDIT_DWS_HOST
AUDIT_DWS_PORT
AUDIT_DWS_DATABASE
AUDIT_DWS_USER
AUDIT_DWS_PASSWORD
AUDIT_DWS_SCHEMA
AUDIT_CORS_ORIGINS
```

可选项：`AUDIT_DATABASE_CONFIG`、`connect_timeout`、`statement_timeout_ms`、`application_name`、`sslmode`、`AUDIT_HOST`、`AUDIT_PORT`。模板默认 `connect_timeout: 10`、`statement_timeout_ms: 30000`、`sslmode: require`；按内网 DWS 的 TLS 策略调整。不要把真实 `.env`、`database.yaml`、`svn.yaml`、日志、SQLite 文件、workspace、缓存或报告输出加入 Git。

SVN 私有配置以 `svn.example.yaml` 为模板，支持 `svn_bin`（不依赖 PATH）、`username`、`password`、`non_interactive`、`trust_server_cert`、`timeout`、每个项目的 `trunk_url` 和 `marker`。建议凭据通过 `${SVN_USER}` / `${SVN_PASSWORD}` 注入。连通性检查（不会在输出中回显密码）：

```bash
"${SVN_BIN:-svn}" info --non-interactive --trust-server-cert "$SVN_BRANCH_URL"
```

## DWS 预检 SQL（只读）

将 `${schema}` 替换为实际 schema 后执行；禁止执行 DROP、TRUNCATE、DELETE 或 DDL 修改生产对象。

```sql
SELECT current_database(), current_user, current_schema();
SELECT 1;

SELECT table_schema, table_name, table_type
FROM information_schema.tables
WHERE table_schema = '${schema}'
ORDER BY table_name;

SELECT sequence_schema, sequence_name
FROM information_schema.sequences
WHERE sequence_schema = '${schema}'
ORDER BY sequence_name;

SELECT table_schema, table_name, privilege_type
FROM information_schema.role_table_grants
WHERE grantee = current_user AND table_schema = '${schema}'
ORDER BY table_name, privilege_type;
```

运行表由 `backend/db/sql/dws/schema.sql` 创建，主键使用 `GENERATED BY DEFAULT AS IDENTITY`，不使用 SQLite 的 `AUTOINCREMENT`、`PRAGMA` 或 `INSERT OR REPLACE`。应用 SQL 经统一路由把 `?` 转换为 PostgreSQL/DWS 的 `%s`。`RETURNING`、`ON CONFLICT`、JSON/JSONB、递归 CTE、数组和特定 DWS 语义仍需由内网 DBA 在目标版本验证；当前仓库不应声称已验证。

最小权限建议：业务运行 schema 中运行表授予应用账号 `SELECT, INSERT, UPDATE, DELETE`；只读元数据表/视图只授予 `SELECT`；identity/sequence（若目标 DWS 暴露 sequence）授予 `USAGE, SELECT`，仅在应用插入需要时授予 `UPDATE`。不要授予 schema owner、DROP 或全库权限。

## 初始化、启动和反向代理

首次部署顺序：

1. 安装 Python、依赖、SVN CLI 和前端 Node/npm 依赖；确认 `psycopg` 可导入。
2. 创建受控 schema，并在维护窗口运行 `python backend/scripts/init_pg.py`（元数据 DDL）和 `python backend/scripts/init_runtime_db.py`（运行表初始化）。先在预生产 DWS 验证 DDL 的幂等性和 identity 默认值。
3. 设置私有环境变量与数据库/SVN 配置，执行下方预检。
4. 构建前端：`cd frontend && npm ci && npm run build`。
5. 用 systemd 启动后端，用 Nginx 托管 `frontend/dist` 并反向代理 `/api/`。

`/etc/systemd/system/code-audit.service` 示例：

```ini
[Unit]
Description=Code Audit API
After=network.target

[Service]
User=codeaudit
Group=codeaudit
WorkingDirectory=/opt/code-audit/backend
EnvironmentFile=/etc/code-audit/backend.env
ExecStart=/opt/code-audit/venv/bin/waitress-serve --host=0.0.0.0 --port=5088 app:app
Restart=on-failure
RestartSec=5
NoNewPrivileges=true
PrivateTmp=true

[Install]
WantedBy=multi-user.target
```

Nginx 示例：

```nginx
server {
    listen 80;
    server_name audit.example.internal;
    root /opt/code-audit/frontend/dist;
    location / { try_files $uri $uri/ /index.html; }
    location /api/ {
        proxy_pass http://127.0.0.1:5088;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

当前应用按第一个 `X-Forwarded-For` 获取审计记录的客户端地址；只应在受信任 Nginx 后暴露后端端口。若启用 HTTPS，应由 Nginx 终止 TLS；若仅 HTTP 内网运行，不能设置依赖 HTTPS 的 Secure Cookie。当前服务没有登录 Session；接入登录前必须显式配置 session secret、HttpOnly、SameSite、Secure 与 CSRF 策略。

## 部署前与冒烟检查

```powershell
git diff --check
D:\miniconda3\python.exe -m compileall backend
D:\miniconda3\python.exe -m unittest discover -s tests
cd frontend; npm test; npm run build
Select-String -Path frontend\dist\assets\* -Pattern 'localhost|127.0.0.1' -SimpleMatch
```

最后一条应无生产 API 命中。部署后依次执行：

1. `GET /api/health` 返回 `status=ok`、`profile=inner_dws`、`type=dws`、`connected=true`，且不含密码、DSN、路径或 SVN 凭据。
2. 加载前端、登录（若已接入）、读取项目列表。
3. 创建最小 SVN 审计任务，查询状态、partial result、最终报告和明细。
4. 核对 DWS 运行表记录、元数据日期/新鲜度字段和应用日志；确认日志无密码。

当前元数据服务没有统一的 freshness 状态/日期契约，且健康检查仅报告数据库与 SVN CLI 可用性。这是内网验证项：必须由 DBA 提供各元数据表或视图的更新时间字段后，才能安全定义 `fresh/stale/missing/invalid` 与阻断阈值；本轮未重构同步业务。

## 回滚

停止 systemd 服务，恢复上一个已验证的后端包和前端静态包，再 `systemctl daemon-reload && systemctl restart code-audit`。数据库初始化前必须保留 DBA 执行的备份/变更记录；本项目不提供对生产数据的自动回滚或破坏性回滚 SQL。
